# 原项目第二阶段：增长贡献分解

这不是另一个演示入口。功能接在原 FastAPI → LangGraph → 三路检索 → DeepSeek 查询计划 → 指标编译 → MySQL → SSE → Vue 链路中。运行 `start_services.cmd` 与 `start_retail.cmd`，访问 http://127.0.0.1:8000 。原压缩包、原 5 行测试配置及私有凭据保持不变。

## 可以直接问

- 2011年11月相比2010年11月，哪些国家贡献了销售额变化？
- 2011年6月相比2010年6月，按商品代码分解销售额增减贡献，展示绝对变化最大的前5组并给出其余贡献。
- 将2011年11月相对2010年11月的销售额变化分解为订单数和客单价的贡献。
- 法国2011年9月相比2011年8月，将销售额变化分解为订单数和平均订单金额各自的贡献。

界面展示总变化、主要贡献、其余分组、核对残差、计算方法和执行依据。SQL、参数、指标版本与只读快照类型可展开复查。金额为 GBP，贡献率为百分比，计算保留精度，页面为便于阅读进行显示舍入。

## 国家 / 商品贡献

先计算两期的完整分组与各自独立总额。每期必须满足“分组金额之和 = 独立总额”，再取两期分组并集计算各组变化。

每组贡献 = 本期该组金额 − 基期该组金额。所有组贡献相加必须还原总变化。按绝对变化排序展示前 N 组，其余合并单列，不能拿两期销售额 Top10 直接相减。

贡献率 = 该组变化 / 总变化，因此可为负、可超过 100%；总变化为零时贡献率未定义，但仍保留正负变化及总变动幅度。

只允许已注册的可加指标 SALES_AMOUNT、UNITS、CANCEL_AMOUNT、LINE_COUNT，以及国家、商品代码互斥分组。去重客户数、去重订单数、客单价和任意比例不能直接加总分组贡献。两期非时间筛选必须相同，避免混用不同人群。

## 订单数 × 平均订单金额

销售额 R = 去重有效订单数 N × 平均订单金额 A。用原始精度的总额和订单数计算 A，不使用展示时四舍五入的客单价。

- 订单数贡献 = (N1 − N0) × (A1 + A0) / 2。
- 客单价贡献 = (A1 − A0) × (N1 + N0) / 2。

相当于对两种替换顺序取平均，避免把交互项全分给某一因素。两项之和应还原销售额变化，核对阈值为 0.000001 GBP。任一期有效订单数为零，客单价未定义，停止分解。

## 完整性与执行边界

- 全部分解查询共用 REPEATABLE READ + WITH CONSISTENT SNAPSHOT + READ ONLY 事务，退出必回滚。
- 普通问数 200 行上限不变。仅服务端注册的完整聚合查询可读取最多 10,001 行，以检测是否超过 10,000 组；超限拒绝，不用截断结果作贡献解释。页面最多展示 50 组。
- 单期缺某个组，只有完整性核对成功后才按“已加载封闭快照内为零”处理，不代表真实世界没有业务。整期无记录不能补零；模型可能提前澄清，执行层也会返回 unavailable。
- 数据来自 UCI Online Retail II，范围为 2009-12-01 至 2011-12-09，首尾年份不完整；不适用于自动解读当前人力政策。
- 新增国家条件覆盖检查：对配置中的 10 个国家中英文别名，检查两期是否保留明确提及的实体；遗漏则要求模型修复一次，仍遗漏就停止。该检查不是通用语义证明，不能证明排除/包含等操作符必然正确，也不覆盖未配置实体与所有复杂范围。
- 失败诊断只输出固定白名单错误码，不输出异常正文、密钥、SQL或业务记录。检索失败不会返回规则或预置答案。

## 为什么仍然不是因果分析

“英国贡献了多少下降”“订单数变化解释了多少金额变化”属于恒等式分解，而不是“某项政策造成了多少增量”。客单价也包含商品组合与订单结构变化，不等于纯价格效应。

当前公开零售数据没有管理政策的处理分配、实施时间、对照组等信息，因此不能验证人力政策的因果准确性。下一阶段如要实现因果评估，应独立增加研究设计：

1. 定义干预、目标人群、结果指标、分析窗口和待估计效应。
2. 优先采用有明确随机分配的数据；观察性数据需要论证混杂控制、共同支持及选择偏差。
3. 若采用差分中的差分，验证处理/对照组、实施时点、处理前趋势、安慰剂与稳健性；不能仅凭有前后数据就执行并给出因果结论。
4. 返回效应估计、置信区间、假设检验、样本和适用范围；假设无法检查时应明确“不足以作因果判断”。

本阶段没有实现或伪装上述因果模块。
