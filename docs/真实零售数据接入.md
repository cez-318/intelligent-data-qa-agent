# 原项目主流程：真实零售数据配置

## 运行

1. 启动 Docker Desktop，再运行项目根目录的 `start_services.cmd`。
2. 运行 `start_retail.cmd`。仍然使用原有 `backend/main.py` 应用，仅选择 `DATA_AGENT_PROFILE=retail_ii`。
3. 打开 http://127.0.0.1:8000 ，确认页头显示 **UCI Online Retail II**，在“服务访问凭据”填写现有 `DATA_AGENT_API_TOKEN`，不是 DeepSeek API 密钥。凭据只保留在当前页内存，刷新后需重填。
4. 例如：“2010年的销售额和去重订单数是多少？”、“按国家统计2011年11月的销售额，取前10名”、“比较2011年11月和2010年11月的平均订单金额”。

如端口被占用，先停止已经启动的旧应用，再切换。旧 `start_app.cmd` 仍运行小样例。不要同时启动两个占用 8000 的实例。也可执行 `.venv\Scripts\python.exe tools\run_retail.py serve --port 8001` 启动独立端口。

## 数据及隔离

来源：[UCI Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii)，Chen, D. (2012)，DOI: 10.24432/C5CG6D，CC BY 4.0。本项目进行了字符串规范化、增加源行号、星型建模和指标派生；不是未经处理的再发布。

- 原文件：`datasets/uci_online_retail_ii/online_retail_II.xlsx`，来源网址、下载时间与本地 SHA-256 在同目录 `source_manifest.json`。本地哈希用于追溯，不是出版方数字签名。
- 1,067,371 行是发票商品**明细**，不是订单数。原始发票号有 53,628 个（包括取消和调整），商品代码 5,304 个，国家/地区 43 个。
- 原始日期：2009-12-01 07:45:00 至 2011-12-09 12:50:00；首尾年份不完整。日期未经人为平移，也不宣称这些是近年业务数据。
- 事实表 `fact_retail_line`，维度 `dim_date`、`dim_country`、`dim_product`；维度键唯一、左连接不增加或丢失事实行。商品名称选同代码最近非空描述，不代表历史时点名称。
- 新库 `dw_retail_ii` / `meta_retail_ii`，新索引 `retail-ii-values-v1`，新向量集合 `retail-ii-column-v1` / `retail-ii-metric-v1`。原 `dw` / `meta` 及原索引不变。
- 查询使用原只读账号，新库只授予 SELECT。元数据账号只管理元数据。原始文件和独立 DuckDB 不对自然语言查询开放。

## 8 个指标

“合格销售明细”定义为：发票非空、不是 C 前缀、数量 > 0、单价 > 0。金额单位 GBP。

| 指标 | 固定口径 |
|---|---|
| SALES_AMOUNT 销售额 | 合格销售明细的数量 × 单价之和；不是净收入或利润 |
| ORDER_COUNT 去重订单数 | 合格销售明细的不同发票号数；不是行数 |
| AOV 平均订单金额 | 销售额 ÷ 去重订单数；零分母返回空值 |
| UNITS 销量 | 合格销售明细数量之和；不是销售额 |
| ACTIVE_CUSTOMERS 活跃客户 | 合格销售中非空客户编号去重数；未知客户不估算 |
| CANCEL_AMOUNT 取消金额 | C 前缀、负数量、正单价明细金额绝对值之和；不是到账退款 |
| CANCEL_INVOICE_COUNT 取消发票数 | 上述取消明细的不同发票号数 |
| LINE_COUNT 原始明细条数 | 包括取消、调整、重复与未知客户的全部原始明细 |

缺失客户编号的 243,007 行保留参与符合条件的销售额。完全相同记录的额外 34,335 行也保留：没有证据证明全部是错误，不能悄悄删除。若业务要求去重，需另建版本并重新生成标准答案，不能混用结果。原始描述缺失 4,382 行，日期缺失 0 行。原始价格非正 6,207 行，负数量 22,950 行：这些不自动解释为错误或退款。

## 可复现步骤

在项目目录使用 `.venv\Scripts\python.exe`：

```text
tools/retail_pipeline.py download
tools/retail_pipeline.py prepare
tools/load_retail_mysql.py --docker <Docker程序绝对路径> --confirm-new-retail-databases
tools/run_retail.py index
tools/run_retail.py serve
```

下载有缓存哈希检查。prepare 和首次导入拒绝覆盖已有结果/非空目标库，避免反复执行意外破坏资料；已经完成的本机不需要重复导入。中断导入应先核对阶段和备份，不能直接删除原库重试。`index` 可对同版本配置重复 upsert，不会刷新已删除字段的旧索引；撤权/删除仍需专门清理流程。

## 评测及证据边界

本机首次完整留出集为 **148/150（98.67%）**，其中一例漏掉国家筛选，一例超出年份时正确说明无数据但未返回约定空结果。原始失败项保留，见 `reports/真实零售数据评测报告.md`。不要把无数据澄清说成金额计算错误，也不要掩盖漏筛选这类实质错误。

`tools/retail_benchmark.py freeze` 从独立 DuckDB 的 `raw_lines` 直接计算标准答案，不调用生产指标编译器，不读取生产派生金额列。冻结的题目/SQL/答案位于 `backend/evaluation/retail_ii_200.json`，相邻 `.sha256` 验证文件是否更改。只将自然语言问题发送给应用，不把标准 SQL 或答案送给模型。

```text
tools/retail_benchmark.py run --split development --confirm-paid-llm-evaluation
tools/retail_benchmark.py run --split test --confirm-paid-llm-evaluation
```

会消耗已配置模型 API 额度。每次结果按时间戳保存到 `reports/retail_live_*.json`，包含每题的成功/失败、HTTP状态、请求ID、SQL、参数、结果、时间。SQL 和参数可能包含被问及的公开客户编号，不含服务密钥。未知或缺期结果不能当作 0；数值容差为金额/计数 0.000001、AOV 0.0001，两期比较同时检查两个查询值与差值/变化率。

本次留出实测使用 `--workers 2`；默认单路。报告明确区分开发集完整首轮47/50、原失败题复测3/3与留出集148/150，不合并成虚假的“200题100%”。

这是 **200 条模板化中文问题实例**：50 开发、150 留出；包括汇总、多指标、国家分组、商品 Top10、月份趋势、同比、无数据与不支持的问题。开发和留出集合共享题型，且由同一开发助手编写，不是独立人员盲测，也不是 200 种独立任务。不得宣传为企业全场景或人力业务准确率。公开数据只有原始记录，没有权威中文问答答案；本项目验证的是已声明指标口径下的可重复执行结果。

性能时间包含模型、检索、SQL和流式传输，受本机 CPU 与网络影响；不是线上 SLA，也不是高并发压测。100万条数据并不代表100万并发或100万用户。

## 尚未完成的部分

- 本轮是“真实数据 + 固定指标 + 独立评测”接入，不是因果推断。数据没有政策干预分组、随机分配或可识别的对照实验，不能证明政策导致增长。
- 因果模块另需确定处理/对照、干预时间、混杂因素、估计对象及假设，再实现效应估计、区间、诊断与拒答。不应让大模型根据普通对比直接给出因果结论。
- 这些是零售数据，不是用友内部人力数据；不能据此虚构人力生产效果或实习指标。
- 商品名称高基数未做全量取值检索；精确商品代码与按代码分组支持，模糊商品名称可能需要澄清。数据没有品类、品牌、利润、员工或部门。
